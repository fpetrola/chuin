## Need

Step 3 of splitting chuin-text into packages under com.fpetrola.chuin.text (PLAN.md, "Paquetes de chuin-text"). What names keys and tells the arrows apart moves to com.fpetrola.chuin.text.input: Arrow and KeyName. Both depend only on com.fpetrola.chuin.input from the API. StreamKeyboard, which stays at the root, reads the arrows through the public Arrow, a dependency that points down, from the root to text.input. The rest of the module names keys from another package (MenuDesktop, to tell a bound key), so KeyName(StringBuilder) becomes public. StreamKeyboard stays at the root for now, because it implements Keyboard and uses Toolkit and Desktop, which are at the API's root. While that root also holds chuin-text classes, moving StreamKeyboard makes a cycle between com.fpetrola.chuin and text.input. It moves in the last step, with TextToolkit, once the root is the API alone; PLAN.md says so. ReadingKeysTest, new, makes a KeyName from outside its package. Nothing changes in behaviour or signature, only the package and the visibility.

## Considered

`com.fpetrola.chuin.input.KeyVisitor#tab(): void` and the rest of the sealed KeyVisitor in chuin-api let anything walk a key, but nothing in the API gives a key a name that two equal keys share. KeyName does that, and the bound keys of the desktop are compared by it.
